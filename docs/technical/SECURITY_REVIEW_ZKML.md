# zkSalaria ZKML Security & Privacy Review

**Date:** November 8, 2025 (Updated)
**Scope:** ZKML Infrastructure (Proof Generation + Verification + Attestation)
**Status:** MVP Implementation Complete - Production hardening pending

---

## Executive Summary

### ✅ SECURE - Good Practices

1. **ZK Proof Privacy** - Individual payment amounts NEVER leave the employee's machine
2. **Cryptographic Verification** - EZKL proofs are cryptographically sound (ZK-SNARKs)
3. **Hash-based Attestations** - Using Midnight-native patterns (not EVM signatures)
4. **Domain Separation** - Verifier public key uses domain-specific hashing
5. **Temp File Cleanup** - Proof files cleaned up after verification
6. **Type Safety** - Full TypeScript with proper interfaces

### ⚠️ MVP COMPROMISES - Intentional for Testing

1. **Hardcoded Secret Key** - Using test key `aaaa...` in `.env`
2. **Sample Data** - Hardcoded payment amounts (Phase 1, will be pluggable)
3. **Single Verifier** - Only one trusted verifier (centralization risk)
4. **Example 1 Model** - Using simple 3-payment averaging (will be upgraded)
5. **No Attestation Ledger** - Contract doesn't verify attestations yet (Phase 2)

### 🚨 SECURITY RISKS - Need Attention

1. **Secret Key Exposure** - Verifier returns secret in attestation response
2. **No Rate Limiting** - Verifier service can be spammed
3. **No Input Validation** - Missing bounds checks on threshold, txid format
4. **Hardcoded Paths** - EZKL binary path hardcoded to `/Users/norman/.ezkl/ezkl`
5. **No Proof Replay Protection** - Same proof can be verified multiple times
6. **No TLS/HTTPS** - Communication in plaintext
7. **CORS Wide Open** - Accepts any origin in development

### 🔒 PRIVACY RISKS - Need Attention

1. **Public Inputs Logged** - Employee ID, threshold logged to verifier service
2. **Attestation Contains PII** - Employee ID stored in attestation
3. **No Anonymity Set** - Can correlate proofs to specific employees
4. **Timestamp Precision** - Unix timestamp reveals exact verification time

### 🚨 SECURITY RISKS

**SECRET KEY EXPOSURE (CRITICAL):**
```typescript
// attestation-signer.ts:79
verifier_secret: this.getSecretKey(),  // ❌ RETURNS SECRET IN RESPONSE
```
```typescript

{
  attestation: {
    verifier_secret: "aaaa...",  // ❌ SECRET LEAKED
    verifier_pubkey: "a0cb..."
  }
}
```
- **Attack:** Anyone can see the verifier's secret key
- **Impact:** CRITICAL - Complete attestation forgery
- **Why This Is Broken:**
  - Verifier secret should NEVER leave the verifier
  - Contract should verify: `hash(data + secret) == attestation_hash`
  - Secret revealed ONLY during contract verification, marked as used
- **Fix Required:**
  ```typescript
  // attestation-signer.ts
  async createAttestation(publicInputs: ProofPublicInputs): Promise<Attestation> {
    return {
      employee_id: publicInputs.employee_id,
      threshold: publicInputs.threshold.toString(),
      txids: publicInputs.txids,
      merkle_root: publicInputs.merkle_root,
      timestamp: timestamp,
      attestation_hash: attestation_hash,
      // verifier_secret: this.getSecretKey(),  // ❌ REMOVE THIS
      verifier_pubkey: this.publicKey
    };
  }
  ```
- **Contract Verification Flow:**
  ```compact
  circuit verify_attestation(
    employee_id: Bytes<32>,
    threshold: Uint<64>,
    // ... other public inputs
    attestation_hash: Bytes<32>,
    verifier_secret: Bytes<32>  // Provided by employee from attestation
  ) {
    // Check not already used
    assert(!used_attestations.contains(attestation_hash));

    // Verify: hash(data + secret) == attestation_hash
    let computed_hash = hash(hash(data) + verifier_secret);
    assert(computed_hash == attestation_hash);

    // Mark as used (prevent replay)
    used_attestations.insert(attestation_hash);
  }
  ```

### 🔒 PRIVACY RISKS

**Public Inputs Logged:**
```typescript
// verify.ts:37-41
fastify.log.info('Received proof verification request', undefined, {
  employee_id: publicInputs.employee_id,  // ❌ PII logged
  threshold: publicInputs.threshold,

})
```
- **Issue:** Verifier learns employee identity
- **Impact:** HIGH - Privacy violation
- **Mitigation Options:**
  1. **Blind Verification:** Use zero-knowledge proof of attestation
  2. **Anonymous Credentials:** Use group signatures
  3. **Trusted Verifier:** Accept that verifier is trusted party
- **MVP Decision:** Accept trusted verifier model
- **Document:** Make clear that verifier sees employee_id

**Attestation Contains PII:**
```typescript
// Attestation includes:
{
  employee_id: "0x742d35...",  // ❌ Identifies employee
  threshold: 5000,
  txids: [...],
  merkle_root: "0x..."
}
```
- **Issue:** Anyone with attestation can link to employee
- **Impact:** MEDIUM - Pseudonymity broken
- **Alternative:** Use nullifier instead of employee_id
  ```typescript
  nullifier = hash(employee_id + "zksalaria:nullifier:" + timestamp)
  // Different per verification, can't be linked
  ```

**No Anonymity Set:**
```typescript

// Can track: "Employee 0x742d35 verified at 12:34pm"
```
- **Issue:** Temporal correlation attacks
- **Impact:** LOW - Privacy leak over time
- **Future:** Batch verification (multiple employees verify together)

**Timestamp Precision:**
```typescript

```
- **Issue:** Reveals exact verification time
- **Impact:** LOW - Timing analysis possible
- **Mitigation:** Round to nearest hour/day
  ```typescript
  const timestamp = Math.floor(Date.now() / 3600000) * 3600;  // Hourly
  ```

## 3. Smart Contract Integration ✅ IMPLEMENTED

### ✅ ACTUAL IMPLEMENTATION

**Circuit:** `submit_income_proof` (payroll.compact:1061-1117)

**Trust-Based Attestation Model:**
```compact
export circuit submit_income_proof(
  employee_id: Bytes<32>,
  proof_type: Uint<8>,           // 1-4 (ABOVE_THRESHOLD, RANGE, AVERAGE, CREDIT_SCORE)
  threshold_min: Uint<64>,
  threshold_max: Uint<64>,
  txids: Vector<12, Bytes<32>>,
  merkle_root: Bytes<32>,
  attestation_hash: Bytes<32>,   // Hash commitment from verifier
  verifier_pubkey: Bytes<32>,    // Public key (NOT secret!)
  timestamp: Uint<64>,
  expires_in: Uint<32>
): Boolean {
  // Step 1: Verify proof type is valid (1-4)
  // Step 2: Check verifier is trusted
  assert(trusted_verifiers.member(verifier_pubkey));

  // Step 3: Check attestation not already used (replay protection)
  assert(!used_attestations.member(attestation_hash));

  // Step 4: Verify timestamp is fresh (within 1 hour)
  assert(timestamp > current_timestamp - 3600);
  assert(timestamp <= current_timestamp);

  // Step 5: Store the income proof
  income_proofs.insert(employee_id, IncomeProof{...});

  // Step 6: Mark attestation as used
  used_attestations.insert(attestation_hash, 1);

  return true;
}
```

**Key Difference from Original Design:**
- ❌ Does **NOT** recompute `hash(data + verifier_secret)`
- ✅ **Trusts** the verifier because their pubkey is in the trusted set
- ✅ Verifier's secret **NEVER** goes on-chain (stays on verifier server)
- ✅ More efficient (no hash recomputation)
- ✅ Follows Midnight trust model (trusted third-party attestation)

**Actual Ledger State:**
```compact
export ledger trusted_verifiers: Set<Bytes<32>>;       // ✅ Implemented
export ledger used_attestations: Map<Bytes<32>, Uint<8>>;  // ✅ Implemented
export ledger income_proofs: Map<Bytes<32>, PC_IncomeProof>;  // ✅ Implemented
```

**Security Properties:**
- ✅ Verifier authentication (only trusted verifiers accepted)
- ✅ Replay protection (attestation can only be used once)
- ✅ Freshness (1-hour validity window)
- ⚠️ Trust-based (doesn't recompute hash - trusts verifier)
- ✅ Verifier secret never exposed on-chain

### Trust Model:

1. **Off-chain:** Verifier cryptographically verifies the ZKML proof using EZKL
2. **On-chain:** Contract trusts the verifier's attestation based on:
   - Verifier is in the trusted set (`trusted_verifiers.member(verifier_pubkey)`)
   - Attestation hasn't been used before (`!used_attestations.member(attestation_hash)`)
   - Timestamp is fresh (within 1 hour)

3. **Security:** Verifier's secret NEVER leaves the verifier server
   - Attestation hash is a commitment: `hash(data_hash + verifier_secret)`
   - Only the verifier can create valid attestations
   - Contract trusts the attestation without needing the secret

## 5. Threat Model

### Attackers:

1. **Malicious Employee**
   - Goal: Forge proof showing higher salary
   - Mitigation: ✅ ZK proof cryptographically sound
   - Status: SECURE

2. **Proof Thief**
   - Goal: Steal employee's proof, claim as own
   - Mitigation: ❌ No proof ownership binding
   - Status: VULNERABLE - Need employee signature

3. **Verifier Operator**
   - Goal: Learn employee salaries, sell data
   - Mitigation: ✅ Verifier only sees threshold result, not amounts
   - Status: ACCEPTABLE - Verifier is semi-trusted party

4. **Attestation Forger**
   - Goal: Create fake attestation without valid proof
   - Mitigation: ❌ Verifier secret exposed
   - Status: CRITICAL VULNERABILITY - Remove secret from response

5. **Replay Attacker**
   - Goal: Reuse old attestation after salary dropped
   - Mitigation: ❌ No replay protection (yet)
   - Status: VULNERABLE - Need used_attestations ledger

6. **Man-in-the-Middle**
   - Goal: Intercept proof, learn employee_id
   - Mitigation: ❌ No TLS
   - Status: VULNERABLE - Need HTTPS in production
